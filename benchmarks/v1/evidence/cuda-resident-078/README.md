## Arithmetic counterexample and limits

The separate [CPU diagnostic](score-symmetry-diagnostic.json) is generated by
[`cuda_score_symmetry.py`](../../cuda_score_symmetry.py), with its own source
hashes, dirty state, environment and command. It is an arithmetic investigation,
not a GPU rerun, CUDA simulator or production backend.

The oracle gives both root candidates gain 2.379372427983539. Their weighted child
summaries are swapped; the only non-complement row assignment is the zero-weight
row. The declared exact-tie rule therefore selects `(0, 0, True)`.

Reconstructing float32 gradients gives child `(G,H)` summaries
`(-3.222222328186035, 2)` and `(3.222221851348877, 7)`, reversed in the other
candidate. Independently rounded child products give equal child-score sums
2.3793725967407227. A grouping that fuses the left product into the addition gives
2.3793723583221436 for the oracle-first candidate and 2.3793725967407227 for the
other: one binary32 ULP, consistent with the observed selection. Fusing the right
product instead reverses that ordering.

This demonstrates a compatible rounding mechanism. **Run 4 did not export these
root candidate gain buffers or PTX/SASS**, so it does not prove which instruction
sequence ran. Reconstructed summaries are not observed GPU buffers. The diagnostic
compares child-score sums, not a captured final gain trace. Histogram accumulation
and generated score code remain hypotheses to distinguish with direct evidence.

## Retrospective and next correction

Resident composition now executes on real hardware, and transaction failures were
not detected in their dedicated checks. The integration fixture nevertheless
exposes a score-ordering correctness gap that the previous 88 primitive cases did
not expose. Keep the composable boundary and repair the numerical contract before
expanding objectives or making a CUDA training acceptance claim.

1. Add a direct swapped-summary score test using the frozen counterexample. Also
   retain strictly unequal adjacent-ULP scores to prevent an epsilon tie band from
   hiding real ordering differences. Preserve all original 202 cases and tolerances.
2. Make the child-score arithmetic explicitly symmetric under swapping children.
   Independently rounded products are a candidate correction: NVIDIA documents
   that `fmul_rn` rounds the multiply independently and prevents merging with an
   addition; numba-cuda exposes this operation. Verify the actual code generation
   and candidate values rather than inferring it from source syntax.
   See [NVIDIA libdevice](https://docs.nvidia.com/cuda/archive/13.0.0/hopper-tuning-guide/libdevice-users-guide/__nv_fmul_rn.html)
   and [numba-cuda libdevice bindings](https://nvidia.github.io/numba-cuda/reference/libdevice.html).
3. Freeze the corrected source and added diagnostics after local checks. A future
   bounded hardware package should capture the two original candidate summaries,
   score bits and relevant generated code, then rerun every original case. It
   requires its own concrete upload/compute allowance; run 4 permits no retry.

No production kernel correction is included in this evidence record. Stop at this
planned retrospective before broader construction. Formal R/C/A/E gates, independent
author accounting, required CUDA recipes, P7 and E4 remain open.
